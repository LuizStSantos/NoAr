## Original security findings and proposed fixes

- **B-001 / SEC-A1: original HIGH finding remains supported; source fix addresses the demonstrated allocation path.** `backend/app/src/graphics.rs` calls `validate_take_fields` before resolving or preparing manual content. `backend/app/src/graphics/templates/graphics.rs` limits 64 fields, 1000 characters per value and 16 record selectors. Its nonallocating `field_parts` visitor sums every visible text layer's fully substituted byte count and rejects totals above 256 KiB before `fill_fields` constructs strings. Both ordinary and controlled spec conversion reach that budget. The cap therefore covers repeated placeholders across layers, not merely the request payload. The API regression `manual_take_rejects_unbounded_fields_before_expanding_text` includes a regular channel user, 1001-character values, 65 fields, 17 record selectors, and a within-per-value-limit expansion exceeding the aggregate cap. I inspected the tests but did not execute them. A multi-GiB/OOM proof is unnecessary and must not be attempted.
- **B-002 / SEC-A2: queue and operator-edit fixes address the original deterministic sequences.** Pending takes are tracked in a bounded 16-entry map, have cancellation tokens with RAII removal, and retain the captured edit/output generation. Out-all, edits and deletion serialize against final take publication using the same channel publication mutex. A scheduled take uses the lock-owning variant rather than reacquiring that mutex. This closes the original queue → delete/out → L-shape-off sequence and bounds retained tasks/specs. Tests inspect capacity, cancellation and released capacity without large allocations. Individual active-take out intentionally cannot address a pending take with no public ID; out-all is the supported cancellation path and the frontend must expose it when only pending work exists.

## Lifecycle edge requiring clarification or regression coverage

`draw_and_take` currently performs its final `version.load` and then `graphics_control.take`/record insertion as separate operations. `ChannelManager::stop_all` and synchronous `GraphicsLifecycleGuard::drop` call `cancel_pending` without acquiring the publication mutex. A possible interleaving is final generation check → output cancellation increments generation → old prepared take publishes. The channel's `GraphicsControl` is reused across subsequent player runs (`player/output/playout.rs` passes the same manager control clone), rather than being visibly cleared at every restart.

This is a **VERIFIED_STATIC concurrency gap**, not an executed stale-output reproduction or a new proven security HIGH. Its user-visible classification depends on the intended linearization point and whether a take logically admitted immediately before stop is allowed to survive like an already-active take. For the strict claim that cancelled pending commands can never reappear after stop, add a small barrier test around final publication versus lifecycle invalidation and an atomic generation-checked publication gate if needed. I relayed this question to the lead. Existing tests cancel while work is still waiting; they do not force this final-check interleaving. Do not describe that stronger race as runtime-verified from those tests.
